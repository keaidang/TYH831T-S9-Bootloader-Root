# 逆向分析记录

本文记录 `uboot_b` 的定位过程与实证数据。**所有地址都来自本机自己的镜像**，不是从别的机型照抄。

---

## 1. 镜像结构

`uboot_b` 分区 3 MB（`0x300000`），是一个 DHTB 容器：

```
0x000        DHTB 头（0x200）
             ├─ 0x08  DHTB 头自身哈希
             └─ 0x30  payload 长度 = 0x109ea0
0x200        原厂 payload（代码 + 数据 + 字符串）
0x10A0A0     SIMGHDR 页脚（0x60）
             └─ 0x18  payload_offset = 0x200
0x10A100     证书区
...          之后是 0 填充到 3 MB
```

校验点：

| 值 | 结果 |
|---|---|
| 文件 SHA256 | `F0BA7AEC4D4FF8A9F51B8218A18253851A5ADC1FA12397703D4B03A221AE877F` |
| payload 长度 | `0x109EA0`（1,089,184） |
| 页脚偏移 | `0x10A0A0` |
| `payload_offset` | `0x200`（未被 magic64 处理过的标志） |

## 2. 加载基址：从设备自己的日志里取，而不是猜

`uboot_log` 分区（16 MB 环形缓冲）里保留了 LK 自己的打印：

```
[00003059] [c0] sprd_get_vboot_key(): load_buf is 0x0xb4fffe00.
[00003064] [c0] sprd_get_vboot_key(): sechdr_offset is 0x10a0a0.
[00004338] [c1] uboot load address is 0xb5000000
[00004338] [c1] sysdump-uboot: addr is 0xb5000000, size is 0x1000000
```

两条独立证据互相印证：

1. `load_buf 0xB4FFFE00` 是 DHTB 头的加载地址，`+0x200` = **`0xB5000000`** = payload 的运行时基址
2. `sechdr_offset 0x10A0A0` 与本机镜像里 `SIMGHDR` 页脚的实际偏移**完全一致** → 证实用的就是这一版镜像

所以：

```
virtual_addr = 0xB5000000 + code_offset
code_offset  = file_offset - 0x200
```

## 3. 定位 `get_lock_status()`

### 3.1 先找锁状态全局变量

安卓侧 11 个读者都读同一个缓存值，反汇编里表现为对 `[x?, #0x8c8]` 的访问：

```asm
0xB5038524: ldr w1, [x1, #0x8c8]     ; AVB 判定
0xB505F918: ldr w3, [x3, #0x8c8]
0xB505FCC0: ldr w0, [x23, #0x8c8]    ; cmp w0,#1 / b.eq
0xB506085C: ...
0xB506086C: str w0, [x1, #0x8c8]     ; ← 写 1（解锁）
0xB5060890: str w20, [x0, #0x8c8]    ; ← 写 0（锁定）
```

全 payload 只有 **2 处写入**，都在同一个函数里 → 这就是锁判定函数。

### 3.2 函数本体

```asm
0xB506080C  stp  x29, x30, [sp, #-0x20]!
0xB5060810  mov  x0, #0x1dc          ; 锁记录长度 0x1dc
0xB506081C  bl   0xB5031470          ; malloc
0xB5060824  cbz  x0, 0xB5060898      ; 失败 -> 错误路径（返回 -0xc）
0xB5060830  bl   0xB5034C9C          ; memset(buf, 0, 0x1dc)
0xB5060834  adrp x0, 0xB50D4000
0xB5060838  add  x0, x0, #0x870      ; 分区名 "miscdata"
0xB506083C  mov  x1, #0x1dc
0xB5060840  mov  x2, #0x2000         ; 偏移 0x2000
0xB5060844  mov  x3, x19             ; 目标缓冲
0xB5060848  bl   0xB503E520          ; 读分区
0xB506084C  cbnz w0, 0xB50608B8      ; 读失败 -> 错误路径
0xB5060858  bl   0xB500B238          ; 校验记录（本地哈希，见 3.3）
0xB506085C  cbnz w0, 0xB5060888      ; ← 校验失败 -> 锁定
0xB5060860  adrp x1, 0xB5113000
0xB5060864  mov  w0, #1
0xB5060868  mov  w20, w0
0xB506086C  str  w0, [x1, #0x8c8]    ; g_DeviceStatus = 1
0xB5060870  ...
0xB5060878  mov  w0, w20
0xB506087C  ldp  x19, x20, [sp, #0x10]
0xB5060880  ldp  x29, x30, [sp], #0x20
0xB5060884  ret
0xB5060888  adrp x0, 0xB5113000
0xB506088C  mov  w20, #0
0xB5060890  str  w20, [x0, #0x8c8]   ; g_DeviceStatus = 0
0xB5060894  b    0xB5060870
```

结论：`g_DeviceStatus` 位于 **`0xB5113000 + 0x8c8 = 0xB51138C8`**。

### 3.3 校验函数是本地实现，不走 TEE

`0xB500B238` 的内部：

```asm
0xB500B238  stp  x29, x30, [sp, #-0x30]!
0xB500B250  mov  x1, #0x80
0xB500B254  mov  x0, #0x1000          ; 分配 0x1000
0xB500B258  bl   0xB50314BC
0xB500B264  sub  w1, w20, #1
0xB500B268  cmp  w1, #0x3f            ; 长度上限 0x40
0xB500B270  ...
0xB500B29C  bl   0xB50349A4          ; memcpy
0xB500B2A8  bl   0xB50A0B94          ; 哈希类运算（0x80 字节块）
0xB500B2AC  ldrb w1, [x19, #0x40]
0xB500B2B0  cmp  w1, wzr
0xB500B2B4  csinv w20, w0, wzr, ne
```

**整个 payload 里 `smc` 指令只有 1 条**，且不在锁判定路径上。所以：锁记录校验是 AP 侧本地计算，不是 TEE 调用。

这也解释了为什么"AP 侧解锁"能成立——改的是 AP 侧缓存，安全世界不知情。

## 4. 补丁点

```
code offset  0x6085C
file offset  0x200 + 0x6085C = 0x60A5C
virtual      0xB5000000 + 0x6085C = 0xB506085C
原指令       0x35000160  (cbnz w0, 0xB5060888)
补丁         0xD503201F  (nop)
```

只改这 4 个字节，函数就永远走"写 1"分支。

## 5. magic64 打包后的布局

```
0x000  DHTB 头（0x200），mImgSize += 0x100
0x200  B <shellcode>            （0x10 字节跳转）
0x210  原厂 payload             逐字节不变（RSA 有效）
...    shellcode 0x70 + patch table 0xNN + 填充 = 0xF0
...    SIMGHDR 页脚（0x60），payload_offset = 0x210，各段偏移 +0x100
...    证书区
```

补丁表格式（每条 12 字节，末尾 4 字节 0 结束）：

```
uint32 runtime_addr
uint32 word_count
uint32 word[...]
```

本机只有一条：

```
addr = 0xB506085C   count = 1   word = 0xD503201F
```

自检：

- 输出大小 == 3,145,728
- 输出 `[0x210 : 0x210+0x109ea0]` 与原厂 `[0x200 : 0x200+0x109ea0]` **逐字节相同**
- 输出 SHA256 应等于 `9E1CF21E9580D01F10D1B0487C67B10EB0ED22FDA0E9D1735D7877C834350F5C`

同一份原厂镜像 + 同一个补丁点 → 永远得到同一个哈希（打包器纯 Python、确定性）。

## 6. 换固件怎么重新定位

脚本对不认识的固件会**直接拒绝**（先校验整文件哈希，再校验原指令字）。换固件时的定位步骤：

```python
import struct
from capstone import *

d = open("uboot_b.bin", "rb").read()
size = struct.unpack_from("<I", d, 0x30)[0]      # DHTB 头的 payload 长度
pl   = d[0x200:0x200+size]
BASE = 0xB5000000

md = Cs(CS_ARCH_ARM64, CS_MODE_ARM)
for ins in mdl.disasm(pl, BASE):
    if ins.mnemonic == "str" and ", #0x8c8]" in ins.op_str:
        print(hex(ins.address), ins.mnemonic, ins.op_str)
```

找到 `str w?, [x?, #0x8c8]` 后，往上翻到函数开头，确认：

1. 有 `mov x0, #0x1dc`
2. 有读 `miscdata` 偏移 `0x2000` 的调用
3. 有一个 `cbnz w0, <锁定分支>` 紧跟在校验调用之后

那个 `cbnz` 的 `code_offset = va - 0xB5000000` 就是新的补丁点。把它的原指令字填进 `EXPECT_WORD`，或直接用：

```bash
python magic64/build_unlock_image.py \
  --input dump/uboot_b.bin --output out/uboot_b_magic64.img \
  --offset 0xXXXXX --skip-hash-check --skip-word-check
```

> `--skip-*` 意味着你自己承担校验责任。改之前务必用 `diff` 确认只改了预期的一个字。

## 7. 关于"刷完没效果"

如果刷入并读回一致、但开机仍是 `flash.locked=1`，可能原因：

1. 活动槽不是 `_b`（本机 `_b`；用 `getprop ro.boot.slot_suffix` 确认）
2. 刷的是 `uboot_a` 而不是当前槽的 `uboot_b`
3. 固件的 `get_lock_status()` 结构与本文不同（换固件未重新定位）
4. 个别机型 LK 会另外缓存判定（本机没有这个问题）

此时先回滚，再重新分析——不要反复盲刷。
